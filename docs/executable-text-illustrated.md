# 噬神者中文化实战：EBOOT.BIN / PRX / SELF 里的文本与指针

> **本文只讲可执行文件侧**：执行程序（`EBOOT.BIN` / `eboot.bin`）和它的模块
> （`.prx` / `.sprx` / `.self`）里的文本怎么改。
> 资源包（`.rdp` / `.res` 等）里的文本是另一套容器，不在本文范围内。
>
> **适用范围**：PSP 的 `EBOOT.BIN` 与 `*.prx` / `*.sprx`，
> 以及 PSVita 的 `eboot.bin` 与 `*.self`（见 §10）。
> 前者是 MIPS，文件打开就是 ELF；后者是 ARMv7-A，外面套着 SELF 壳、里面的段还可能压过 ——
> **先用 FAGDec 脱壳出 ELF 再改，改完用 vita-elf-inject 注回**。
> **改法一致，只是指令集换了一套。**
>
> **本文的定位**：前面讲的是"文本存在哪、指针长什么样"，
> 但**真正动手改的时候，90% 的时间花在两件事上**：
> ① 这条中文放不放得进原来那个位置；② 放不进去搬走之后，**谁还指着旧地址**。
>
> 本文用**同一份文件的两个版本**（日版 / 繁中版），把这两件事从头到尾拆开讲：
> 1662 个差异字节，88 个差异区间，**全部对得上账**。
>
> 阅读顺序建议：先看 §0.1（这几个文件各是什么）、§1–§2（文件长什么样、差异在哪），
> 再看 §3（文本区怎么排）、§4（改指针）、§5（改指令），
> 然后看 §6（决策表）、§7（实操流程）、§9（EBOOT.BIN）、§10（PSVita）。

## 0. 先建立一张地图

### 0.1 先说清楚这几个文件在游戏里各是什么

PSP 上的噬神者，文件分工是这样的：

| 文件 | 角色 | 格式 |
|---|---|---|
| `EBOOT.BIN` | **执行文件**（主程序） | PRX（`\x7fELF` 外壳，`e_type=0xFFA0`） |
| `*.prx` | 随主程序加载的**依赖模块** | PRX |
| `*.sprx` | **更新补丁里的同名模块** | PRX，**与 `.prx` 完全同构** |

系统真正启动的是 `EBOOT.BIN`；界面、战斗、音声这些功能模块各自编成 `.prx`，由它按需加载。
打了更新补丁之后，补丁目录里会带一份同名的 `.sprx` —— 加载时**优先用补丁版覆盖原版**。

**所以 `.sprx` 不是另一种格式**，它就是"放在补丁里的 prx"，只差一个字母。
本文实战用的 `layout.sprx` 正是更新补丁里的那一份 —— 因为它才是游戏实际加载的模块，
改原版镜像里的 `.prx` 反而可能被补丁盖掉、白改。

> 一句话：**改 prx 和改 sprx 在字节层面是同一件事**，
> 区别只在这份文件是从原版镜像里拿的，还是从更新补丁里拿的。
>
> PSVita 版的对应关系见 §10：执行文件同样叫 `eboot.bin`，
> 依赖模块是 `.self`，两者都是「SELF 头 + 内层 ELF」，里面的段还可能被 zlib 压缩 ——
> **改之前先用 FAGDec 把壳脱掉、只留 ELF**，翻译全程以这个 ELF 为基准，
> 改完再用 vita-elf-inject 注回 `eboot.bin`；
> 指令集从 MIPS 换成 **ARMv7-A**。

### 0.2 样本不是 ELF，是 "ELF 的壳"

`layout.sprx` 头 4 字节是 `7F 45 4C 46`（`\x7fELF`），
但 `e_type` 不是常见的 `0x0002`（ET_EXEC），而是 **`0xFFA0`** ——
这是 SCE 的 **PRX**（PlayStation 可重定位模块）。

```
文件头（ELF32，小端，MIPS）
   │
   ├─ Program Header × 3
   │     PH0  代码 + 只读数据（含 .rodata 文本）   R+X
   │     PH1  可写数据（含指针槽与 .bss 影子）      R+W
   │     PH2  模块信息（导出/导入/重定位）          只读
   │
   └─ 没有 Section Header（e_shoff = 0，e_shnum = 0）
```

**第一件要知道的事：这个文件没有节表。**
所以你没法用 `readelf -S` 找 `.rodata`、`.data`，
只能靠 **Program Header** 划范围，或者干脆"全文件扫"。

### 0.3 文本在哪，指针在哪

```
layout.sprx（1,250,156 字节）
├─ 0x0000A0 .. 0x10E5E8   PH0 代码段（filesz 0x10E548）
│    ├─ 0x0000A0 .. 0x0F14xx   真正的 MIPS 指令
│    └─ 0x0F14F0 .. 0x0F4E81   ★ .rodata：UTF-8 文本全在这里
│                                （夹着少量 ASCII 调试串，如 src/xxx.cpp）
│
├─ 0x10E5F0 .. 0x112430   PH1 数据段（filesz 0x3E40）
│    └─ 0x10F4DC .. 0x10F95C   ★ 指向日文文本的 32 位指针槽集中在这一段
│                                （整个 PH1 共有 1,878 个合法字符串指针槽）
│
└─ 0x112430 .. 0x13136C   PH2 模块信息
```

> PH1 的 `p_memsz`(0xBEA4) 比 `p_filesz`(0x3E40) 大 0x8064 字节 ——
> **那部分 .bss 不在文件里**，加载时才分配并清零。
> 所以改数据只能改 `0x10E5F0 .. 0x112430` 这段，往后就是文件之外了。

**记住这张表就够了**：文本在代码段尾部（只读区），指针在数据段（可写区）。

> **`EBOOT.BIN` 是同一张地图、换了刻度**：`VA` 从 `+0xA0` 变成 `+0xC0`，
> 文本还在 PH0 里（`0x19F414` 之后的数据区，vaddr `0x2D4000`–`0x2F6200`），
> 但指针不在 PH1，而是和文本挤在同一块数据里的数组。详见 §9。

### 0.4 换算公式（PSP）

```
file_offset = vaddr + 0xA0
vaddr       = file_offset - 0xA0
```

`0xA0` 是 ELF 头 + 3 个 Program Header 的总长度。两段**共用同一个偏移**：

| 段 | p_offset | p_vaddr | 差值 |
|---|---|---|---|
| PH0 | `0x0000A0` | `0x000000` | `0xA0` |
| PH1 | `0x10E5F0` | `0x10E550` | `0xA0` |
| PH2 | `0x112430` | —（不映射） | — |

> ⚠️ **不要假设所有 PRX 都差 0xA0**。PH 数量不同，差值就不同。
> 正确做法：用每段自己的 `p_offset - p_vaddr` 分别算。本例正好两段相同。
>
> **PSVita 要先脱壳**：`eboot.bin` / `.self` 不是 ELF，得用 FAGDec 解出 ELF，
> 之后 `file = p_offset + (vaddr − p_vaddr)`，其中 vaddr 从 `0x81000000` 起算。
> 注意脱壳会解压，SELF 里的偏移和 ELF 里的偏移**不是固定差值**（§10.1.1）。
> 详见 §10.1.4。

## 1. 两个样本

### 1.1 为什么选这两个

| | 日版 | 繁中版 |
|---|---|---|
| 路径 | `jp/bin/layout.sprx` | `cn/bin/layout.sprx` |
| 大小 | 1,250,156 | **1,250,156**（一模一样） |
| 差异字节 | — | **1,662** |
| 差异区间 | — | **88** 段 |

两份都是**更新补丁目录里的 `layout.sprx`**（§0.1 说的那种"补丁 prx"），不是原版镜像里的同名模块 ——
因为补丁会覆盖原版，只有补丁里这份才是游戏实际加载的字节。
文件名是 `.sprx` 而不是 `.prx`，但格式一字不差，下文的判据对 `.prx` 同样成立。

**大小完全相同** —— 这本身就是一条重要线索：
中文化是**纯原地改写**，没有插入、没有搬段、没有改头。
所以整篇文章只需要回答一个问题：**改了哪些字节，为什么要改**。

> **本文给的是方法和判据，不是可以直接照抄的偏移表。**
> 文中出现的每一个地址（段偏移、槽位、字符串位置、指令地址）
> 都取自这一对样本，换成别的版本、别的语种，位置全都会变。
> 本文也**不提供批量扫描脚本** —— 段布局、串池范围、编译器排布各版本都不同，
> 照抄脚本会把版本差异和伪命中一起带进来，比手工核对更容易改错。
> 找位置这一步，按 §4.5、§5.6 给的判据，对着自己手上的版本做。

### 1.2 Program Header 逐字段

`e_phoff = 0x34`，`e_phnum = 3`，每项 32 字节：

```
0x0034  01 00 00 00 | a0 00 00 00 | 00 00 00 00 | 5c db 0e 00
        p_type=1     p_offset      p_vaddr       p_paddr=0xEDB5C
        48 e5 10 00 | 48 e5 10 00 | 05 00 00 00 | 10 00 00 00
        p_filesz      p_memsz       p_flags=RX    p_align=16
        ↑ 0x10E548    ↑ 0x10E548
          文件里有      内存里要
          （两者相等 ⇒ 这一段没有 .bss）

0x0054  01 00 00 00 | f0 e5 10 00 | 50 e5 10 00 | 00 00 00 00
        p_type=1     p_offset      p_vaddr       p_paddr
        40 3e 00 00 | a4 be 00 00 | 06 00 00 00 | 10 00 00 00
        p_filesz      p_memsz       p_flags=RW    p_align=16
                     ↑ 0x3E40      ↑ 0xBEA4
                       文件里有      内存里要
                       0x3E40 字节   0xBEA4 字节
                                     （多出来的是 .bss）

0x0074  a1 00 00 70 | 30 24 11 00 | 00 00 00 00 | 00 00 00 00
        p_type=0x700000A1  p_offset    p_vaddr       p_paddr
        3c ef 01 00 | 00 00 00 00 | 00 00 00 00 | 10 00 00 00
        p_filesz      p_memsz=0     p_flags=0
        ↑ 0x1EF3C
```

**PH1 的 `filesz`(0x3E40) < `memsz`(0xBEA4)** ——
说明数据段里有 **0x8064 字节是 .bss**，文件里不存在，加载时清零。
对我们来说只有一个含义：**改指针只能改 `p_offset .. p_offset+0x3E40` 之间**，
越界就是改到 .bss 的影子上了（那是垃圾数据，会被加载器覆盖）。

### 1.3 校验：偏移公式对不对

拿一处已知内容验证：

```
vaddr 0x0F147C  +  0xA0  =  file 0x0F151C
                               ↓
              e3 82 b9 e3 82 bf ...  =  "スタングレネード持ちこみ可能数（一人当たり）"
```

而数据段 `0x10F4DC` 处的 u32 值正好是 `0x000F147C`。
**指针 → vaddr → file offset 三者严丝合缝。**

### 2.2 为什么差异段是 88 个而不是 3 个

因为热区② 里，只有"被翻译过"的字符串才是差异。
没翻译的（`src/missionorder/*.cpp`、`AVATAR`、`REGULAR`、`難易度1`…）一个字节都没动。

所以 74 个差异段的含义是：**74 处文本被改写**（有些是同一段里连续多条）。

### 2.3 一个关键观察：只有 13 个指针改了

热区③ 里共有 13 个槽位发生了改动。

而热区② 里被翻译的字符串有几十条 —— **为什么只有 13 个指针需要动？**

答案在下一节：**因为绝大多数中文比日文短，能原地塞回去。**

## 3. 热区②：文本区

### 3.1 编码统一是 UTF-8

这套引擎的文本资源**从头到尾只用 UTF-8 一种编码**：日版是 UTF-8 的日文，
繁中版是 UTF-8 的汉字，两版之间除了文本内容本身，编码方式一模一样。

**整个游戏不存在 Shift-JIS 编码的文本**，所以：

- 不需要写"先猜编码"的逻辑，也不必维护两套解码器 —— 一律按 UTF-8 读。
- 不要因为「PSP 时代的日文游戏」这个印象就先去试 Shift-JIS，
  那样会把本来正确的字节解成乱码，误判成"字符串被加密/压缩了"。

字节形态：

```
e3 82 b9 e3 82 bf e3 83 b3 e3 82 b0 e3 83 ac ...
└── ス  ┘└── タ  ┘└── ン  ┘└── グ  ┘└── レ  ┘
        每个假名 3 字节（e3 81/82/83 xx）
```

`e3 81 xx` 是平假名（U+3040–U+309F），`e3 82/83 xx` 是片假名（U+30A0–U+30FF），
`e4–e9 xx xx` 是汉字区（U+4E00–U+9FFF）。

**验证方法**：直接从字符串起点按 UTF-8 严格解码，能全部解出、没有替换字符就对了。
如果解不出来，那不是编码问题 —— 是**起点没落在字符边界上**（偏移算错、或跨进了
上一条的填充区），退到最近的 `00` 之后或 4 字节对齐处重解即可，不要换编码再试。

> 这条决定了后面所有长度计算：**一个汉字 3 字节**，一个假名 3 字节，
> ASCII 1 字节。中文和日文在这里是**同一套编码、同一种字节宽度**，
> 所以"翻译成中文"通常会让字符串**变短**（日文假名多、中文用字少）。

### 3.2 字符串怎么排：两段完全不同

文本区里其实混着两种排布，处理方式**完全相反**：

```
0x0F1518 ─┬─ 段 A：原地替换 + 补零（偏移一个都不变，指针不用改）
0x0F16EA ─┘      "スタングレネード持ちこみ可能数（一人当たり）" → "可攜帶昏迷榴彈數量（每人）"
0x0F16EA ─┬─ 中间：纯 ASCII 调试串（src/missionorder/*.c、missionparserXXX）
0x0F1C04 ─┘     两版完全一致，一个字节没动
0x0F1C04 ─┬─ 段 B：紧排字面量（长度一变，后面全部漂移）
0x0F4E81 ─┘      → 必须改指针
```

### 3.3 段 A：为什么偏移一个都没变

先看事实。同样提取两版的字符串，**地址完全对齐**：

| 偏移 | 日版 | 繁中版 | 日版字节 | 中文字节 |
|---|---|---|---|---|
| `0x0F1560` | `クリスマスパック` | `聖誕包` | 24 | 9 |
| `0x0F157C` | `漆黒の捕喰者` | `漆黑捕食者` | 18 | 15 |
| `0x0F1590` | `ニューイヤーパック` | `新年包` | 27 | 9 |
| `0x0F15AC` | `アニバーサリーパック` | `周年慶包` | 30 | 12 |
| `0x0F163C` | `難易度1` | `難易度1` | 10 | 10（未译） |
| `0x0F16B4` | `チャレンジ` | `挑戰` | 15 | 6 |

中文比日文短了 3 到 18 字节，**但下一条仍然从原地址开始**。
说明这里是**按原日文长度预留了固定空间**，中文写进去之后，剩下的填 0。

```
0x0F1560  クリスマスパック\0\0\0\0         (28 字节槽)
0x0F157C  ↓ 下一条从这开始 —— 两版一致
          
0x0F1560  聖誕包\0 ..........（补 0 到 0x0F157C）
0x0F157C  ↓ 还是从这开始
```

**段 A 的原始字节：**

```
000f1510  00 00 00 00 00 00 00 00 10 00 06 06 e3 82 b9 e3   ← "10 00 06 06" 是 4 字节非文本头
000f1520  82 bf e3 83 b3 e3 82 b0 e3 83 ac e3 83 8d e3 83     スタングレネード(續)
...
000f1550  ba ba e5 bd 93 e3 81 9f e3 82 8a ef bc 89 00 00     …たり）、\0\0
         ↑ 字符串止于 0x0F155D（"）"），0x0F155E 是 \0，0x0F155F 补 0
```

> **注意 `0x0F1518` 的 `10 00 06 06`**：它不是文本，是这段结构的头部
> （指针槽指向的是 `0x0F147C`，正好跳过这 4 字节）。
> 繁中版**原样保留**了它 —— 翻译时不要顺手把它改掉。

**段 A 的处理规则：原地写、补零、绝不越界。**
好处是指针不用动（`0x10F4DC`–`0x10F530` 那 22 个槽在两版中完全相同）。
坏处是**长度上限被日文锁死** —— 中文一旦比日文长，只能截断或改写。

### 3.4 段 B：为什么后面的全挪了

段 B 是正常的字符串字面量池，**紧密排列、只按 4 字节对齐**：

```
规则： 每个串以 00 结尾，然后补 0 到 4 字节边界
       下一串起点 = align4( 本串起点 + 字节数 + 1 )
```

拿「排序选项」这三条算一遍就明白了：

```
日版
  0x0F1D2C  "登録順"      9 字节 + \0 = 10 → 0x0F1D36，align4 → 0x0F1D38
  0x0F1D38  "名前順"      9 字节 + \0 = 10 → 0x0F1D42，align4 → 0x0F1D44
  0x0F1D44  "同行回数順"  15 字节+ \0 = 16 → 0x0F1D54，align4 → 0x0F1D54
  0x0F1D54  "AVATAR"

繁中版
  0x0F1D2C  "登錄順序"    12 字节+ \0 = 13 → 0x0F1D39，align4 → 0x0F1D3C   ↑ +4
  0x0F1D3C  "名字順序"    12 字节+ \0 = 13 → 0x0F1D49，align4 → 0x0F1D4C   ↑ +8
  0x0F1D4C  （空洞，8 字节 0）
  0x0F1D54  "AVATAR"      ← 靠那个空洞，又回到了原地址
```

**这一段很能说明问题**：
「登録順」→「登錄順序」从 3 字变 4 字，多 4 字节；
「名前順」→「名字順序」同样多 4 字节；
两条加起来前移 8 字节 —— 但「同行回数順」被搬走了，留下 8 字节空洞，
于是后面又对齐回去了。

> **这就是段 B 的现实**：长度一变，后面**连锁漂移**；
> 但作者可以靠"搬走一条 + 留洞"来把漂移**重新归零**，
> 从而让后面的指针全部不用改。

### 3.5 放不下怎么办：搬走、留洞、改指针

「同行回数順」(15B) → 「同行次數順序」(18B+1=19B)。
原位置 `0x0F1D44` 后面紧跟着 `0x0F1D54` 的 `AVATAR`，只有 16 字节，**放不下**。

于是它被搬到了 **`0x0F1FBC`**（vaddr `0x0F1F1C`），
而原来在那里的「はい / いいえ / ミッションキャンセル」被整体后移：

```
日版
  0x0F1FBC  "はい"                     (v 0x0F1F1C)
  0x0F1FC4  "いいえ"                   (v 0x0F1F24)
  0x0F1FD0  "ミッションキャンセル"      (v 0x0F1F30)
  0x0F1FFC  "src/missionorder/..."

繁中版
  0x0F1FBC  "同行次數順序"  ← 搬过来的（v 0x0F1F1C）
  0x0F1FD8  "是"            ← 后移 0x1C（v 0x0F1F38）
  0x0F1FDC  "否"            ← 后移 0x18（v 0x0F1F3C）
  0x0F1FE0  "取消任務"      ← 后移 0x10（v 0x0F1F40）
```

**一旦搬走，所有指向旧地址的指针就全部失效。**
这就是热区③ 存在的唯一原因。

### 3.6 段 B 的实操规则

| 情况 | 做法 | 后果 |
|---|---|---|
| 中文 ≤ 日文长度，且能塞进对齐余量 | 原地写 + 补 0 | 指针不动 |
| 中文超出原位置可用空间 | 搬到空闲区/文件尾空闲字节 | **必须改所有引用它的指针** |
| 中文更短 | 原地写 + 补 0，**不要**把后面的串往前挤 | 指针不动（推荐） |

> **最重要的一条**：**能不动指针就不动指针。**
> 改指针 = 每一个引用点都要找全，漏一个就是乱码或崩溃。

## 4. 热区③：数据段指针槽 —— 直接修改指针

### 4.1 槽长什么样

数据段 `0x10F4DC`–`0x10F95C` 是一串 **u32**，每个都是一条字符串的 vaddr：

```
0x10F4DC: 7c 14 0f 00   →  0x000F147C  → file 0x0F151C  "スタングレネード持ちこみ可能数（一人当たり）"
0x10F4E0: c0 14 0f 00   →  0x000F14C0  → file 0x0F1560  "クリスマスパック"
0x10F4E4: dc 14 0f 00   →  0x000F14DC  → file 0x0F157C  "漆黒の捕喰者"
0x10F4E8: f0 14 0f 00   →  0x000F14F0  → file 0x0F1590  "ニューイヤーパック"
...
```

**它们是绝对地址（vaddr），不是索引、不是偏移、不是相对基址的量。**
所以改法极其简单：**把 4 个字节换成新字符串的 vaddr 就行**，小端写。

### 4.2 为什么改指针不会破坏重定位

PRX 是**可重定位模块**：加载器会把数据段里所有指针统一加上模块基址（加性重定位）。

```
文件里       槽 = 0x000F1CA4
加载后       槽 = 0x000F1CA4 + base
```

你把它改成 `0x000F1F1C`，加载后就变成 `0x000F1F1C + base` —— **依然正确**。

> 前提是重定位类型是 `R_MIPS_32`（加性）。PSP PRX 就是这么做的。
> 如果哪天遇到"绝对覆盖"型重定位（少见），改值就会被加载器覆盖回去，
> 那时只能改代码或改重定位表。本例不存在这个问题。

### 4.3 13 处改动，逐条对账

| # | 槽 file off | 槽 vaddr | 日版值 | 繁中值 | 日版串 | 繁中串 | 移动量 |
|---|---|---|---|---|---|---|---|
| 1 | `0x10F778` | `0x10F6D8` | `0x0F1C98` | `0x0F1C9C` | 名前順 | 名字順序 | +4 |
| 2 | `0x10F77C` | `0x10F6DC` | `0x0F1CA4` | `0x0F1F1C` | 同行回数順 | 同行次數順序 | **+0x278** |

这就是 §3.5 说的"搬走"。

### 4.4 为什么几十条翻译，只有 13 个指针要改

因为段 B 里的漂移**大部分被抵消了**：

1. 中文普遍比日文短 → 后面的串往前挪
2. 但 4 字节对齐会吃掉一部分余量
3. 作者刻意"搬走几条 + 留洞"，让总长度回到原来的位置

结果是：段 B 里 600 多条字符串中，**偏移真正变了的只有十几条**。

反过来说：**这 13 处是"必须改"的最小集合**。
如果漏改任何一处，游戏里对应位置就是乱码 / 显示成别的文本 / 甚至读到越界。

### 4.5 怎么判断一个 4 字节是"指针"而不是别的数

本文不提供一键扫描脚本 —— 各版本的段偏移、串池范围、槽位分布都不一样，
照抄脚本只会把版本差异和伪槽一起带进来。
判断标准只有四条，按这个去找：

1. **位置**：在可写数据段里（`flags` 含 `W`），且 4 字节对齐；
2. **数值**：读成小端 u32 后，落在 `.rodata` 的 vaddr 范围内
   （本例 `0x000A0000`–`0x0010E548`，具体范围看你自己那版的 PH 表）；
3. **目标**：按 `vaddr + 0xA0` 换算到 file offset，那里必须是一个
   以 `00` 结尾、能用 UTF-8 完整解码的串 ——
   解不开就说明这不是指针，只是恰好数值落在范围内的指令或其他数据；
4. **语义**：这个槽对应的界面位置，显示的就是这条串。

第 3 条是筛掉伪槽的关键。代码段里的指令、字库里的二进制，
读成 u32 也会偶尔落进 `.rodata` 范围，只靠数值范围判断会误判一堆。

**改之前先把改动前后的两个版本按 file offset 对齐看一遍**：
槽值变了的地方，就是必须核对的地方；槽值没变但目标串变了，说明串是原地替换，不用管。
变了的槽还要再看一眼新值指向的串对不对 —— **值变了不等于改对了**，可能改错串。

## 5. 热区①：代码段硬编码地址 —— 修改指令索引

> **先解释"指令索引"这个词**：这里的"索引"指的是指令编码里的 `imm` 字段。
> 它相对于 `lui` 给出的 64KB 基址做偏移 ——
> 本质就是"**在哪个 64KB 段里的第几个字节**"，也就是一个索引。
>
> 改它 = 改这个索引。它和 §4 的"指针"是**同一个地址的两种存在形式**：
> 一种躺在数据里（4 字节，可整块覆盖），一种烧在指令里（2 字节 imm，只能原地改）。

### 5.1 有些地址不在数据段，在指令里

MIPS32 没有"立即数 32 位"的指令，所有的绝对地址都是**两条指令拼出来**的：

```asm
lui   $reg, 0xHI        # $reg = 0xHI << 16
addiu $reg, $reg, 0xLO  # $reg = 0xHI<<16 + 0xLO   ← 这就是完整的 vaddr
```

**这个地址是编译期常量，写死在指令的立即数字段里。**
数据段里没有对应的槽可以改 —— 要让代码指向新地址，只能改指令本身。

### 5.2 改动点：0x087844

```
日版 00087838  0f 00 06 3c   lui    $a2, 0x000F
     0008783C  21 38 a0 03   move   $a3, $sp
     00087840  21 20 a0 02   move   $a0, $s5
     00087844  f4 4e c6 24   addiu  $a2, $a2, 0x4EF4    ← $a2 = 0x000F4EF4
     00087848  95 b5 03 0c   jal    0x000ED654
     0008784C  20 00 05 24   addiu  $a1, $zero, 0x20     ← delay slot: 长度 32

繁中 00087844  8c 4b c6 24   addiu  $a2, $a2, 0x4B8C    ← $a2 = 0x000F4B8C
```

**只改了 2 个字节**（`F4 4E` → `8C 4B`），指令 opcode 和寄存器全不变。

### 5.3 这两个地址各是什么

```
0x000F4EF4  →  file 0x0F4F94  →  "%s 他"      ← 日版："%s 等（其他人）"
0x000F4B8C  →  file 0x0F4C2C  →  "%s 其他"    ← 繁中版：新写的
```

改动前后语义：`"%s 他"` → `"%s 其他"`。
（一个格式化模板，用来拼"某某 等"这种多人列表的显示名。）

### 5.4 为什么不能原地改，非要改指令

看原位置周围的字节：

```
日版 0x0F4F94
  000f4f94  25 73 20 e4 bb 96 00 00 | 25 73 20 78 25 64 00 00
            "%s 他\0"  + 1 字节填充   "%s x%d\0"
            ↑ 7 字节                    ↑ 紧接着下一条，一点空隙都没有
```

`"%s 他"` = `25 73 20` + `e4 bb 96` + `00` = **7 字节**，对齐后占 **8 字节**。
`"%s 其他"` = `25 73 20` + `e5 85 b6 e4 bb 96` + `00` = **10 字节**。**放不下。**

于是繁中版换了位置 —— 塞进 `0x0F4C2C` 的一个**天然空洞**：

```
日版 0x0F4B78
  000f4b78  "ジーナ・ディキンソン"  (30 字节)  → 0x0F4B96
  000f4b96  00 00                              (2 字节填充)
  000f4b98  "\x07!! Warning !! : ..."          ← 下一条从这里开始

繁中 0x0F4B78
  000f4b78  "吉娜‧狄金森"          (18 字节)  → 0x0F4B8A
  000f4b8A  00 00                              (2 字节)
  000f4b8C  "%s 其他"  (10 字节)   ← ★ 新增的串塞进来了
  000f4B96  00 00
  000f4b98  "\x07!! Warning !! : ..."          ← 位置没变！
```

**这一段是整篇文档最漂亮的地方**：
中文比日文短了 12 字节 → 腾出空洞 → 把新串精确填进空洞 →
**没有移动任何已有字符串，没有改任何数据段指针**，只改了一条指令的立即数。

### 5.5 代码段里有多少这种硬编码

按 §5.6 的判据在本例的 PH0 里核对，`lui + addiu/ori` 拼出、且落在 `.rodata`、
指向含日文/汉字串的有（下面的数字只描述本例，换版本必然不同）：

| 项 | 数量 |
|---|---|
| 代码段里"lui+addiu 指向字符串"的总处数 | 2,206 |
| 其中指向**含日文/汉字**的串 | **31 处**（去重后 26 个不同目标串） |
| 繁中版**实际改动**的 | **1 处** |

为什么 31 处只改了 1 处？

因为另外 30 处指向的串都能**原地替换**（中文更短），
地址没变，代码自然不用动：

| 硬编码地址 | 指向的串 | 中日是否同位 |
|---|---|---|
| `0x0F88DC` | `参照解決 成功.\n` | ✓ 同位（已翻译，未移位） |
| `0x0F4B18` | `カレル・シュナイダー` | ✓ 同位 → `卡雷爾‧許奈德` |
| `0x0F4DDC` | `なし` | ✓ 同位 → `無` |
| `0x0F4EF4` | `%s 他` | ✓ 同位（**但放不下 `%s 其他`，所以另起一处**） |
| … | … | … |

> **注意 `%s 他` 这一行**：它在原位置**仍然存在**（繁中版没删它）。
> 繁中版的做法不是"改这条串"，而是"**新写一条 + 让代码指过去**"。
> 这样可以保留原始串（有些调试输出还会用到），也不影响任何其他引用。

### 5.6 怎么找：代码里的地址长什么样

本文不给扫描脚本，各版本的代码布局、编译器优化都不一样，扫出来的东西要一条条自己核。
要找的形态只有一种 —— **`lui` + `addiu`/`ori` 两步拼出一个 32 位值，而这个值落在 `.rodata` 里**：

```
lui    $a2, 0x000F          # 高 16 位
addiu  $a2, $a2, 0x4EF4     # 低 16 位 → 0x000F4EF4
```

判据：

1. 两条指令**用同一个寄存器**（`rs` = `rt` = `lui` 的 `rt`）；
2. 两条之间间隔 1~4 条指令，**中间不能再出现写同一个寄存器的 `lui`**（出现了就说明配错了对）；
3. 拼出来的值转成 file offset 后，落在一个以 `00` 结尾的合法 UTF-8 串上；
4. 这条串是该界面位置显示的文本。

第 3、4 条一样是筛伪命中的关键：`lui` 也常用来构造 32 位常量、掩码、
浮点数高位，它们的值同样可能偶然落进 `.rodata` 范围。

实际做法是先定位你要改的那条串，再回来找"谁指着它" ——
比先把整段指令过一遍再逐条核对要快得多，也不会被别处的数值常量干扰。

### 5.7 两个必须知道的坑

**坑 1：`addiu` 的立即数是有符号的。**

目标地址低 16 位 ≥ 0x8000 时，编译器会让 `lui` 的高位 **+1**，`addiu` 用负数。
例如 `0x000F9000` 通常是：

```asm
lui   $a0, 0x0010        # 0x0010 << 16 = 0x00100000
addiu $a0, $a0, 0x9000   # 有符号：0x9000 = -0x7000
→ 0x00100000 - 0x7000 = 0x000F9000 ✓
```

写工具时**必须按有符号处理**，否则算出来的地址会和 `lui` 的 0x000F 差 0x10000。

本例恰好两个地址（`0x4EF4` / `0x4B8C`）都 < 0x8000，所以是直白的加法。

**坑 2：跨 64KB 边界要连 `lui` 一起改。**

`lui` 提供高 16 位，`addiu` 提供低 16 位。
如果新旧地址的高 16 位不同（比如 `0x000F4B8C` → `0x00104B8C`），
只改 `addiu` 是不够的，**必须同时改 `lui` 的立即数**。

本例高 16 位都是 `0x000F`，所以只改 `addiu` 一条。

> **实操建议**：尽量把新串放在**同一个 64KB 段内**（本例 `0x000F????`），
> 这样永远只需要改一条指令的 2 个字节。

## 6. 两种改法的分工

把上面的东西收成一张决策表：

| | ① 数据段指针槽 | ② 代码段硬编码地址 |
|---|---|---|
| 地址存在哪 | PH1 里的 u32 槽 | `lui` + `addiu/ori` 的 imm 字段 |
| 表现在 | `0x10F4DC`–`0x10F95C` | `0x087838`+`0x087844` |
| 改动字节 | 4 字节 / 处 | 2 字节 / 处（跨段则 4 字节） |
| 本例改动数 | **13 处** | **1 处** |
| 重定位 | 加载时 `+base`，改值安全 | 同样 `+base`，改 imm 安全 |
| 怎么找 | 判据见 §4.5（四条） | 判据见 §5.6（四条） |
| 漏改的后果 | 显示错串 / 乱码 / 越界读 | 同上，更严重（可能崩溃） |
| 改的时候要注意 | 小端写入，值是 **vaddr** 不是 file offset | imm 有符号；跨 64KB 要连 `lui` 改 |

**一句话概括分工：**

> **地址写在"数据"里的，改数据（4 字节）；地址写在"指令"里的，改指令（2 字节）。**
> 两者改的都是 `vaddr`，都要求新地址落在 `.rodata` 内、且指向一个以 `00` 结尾的合法 UTF-8 串。

### 6.1 还有第三种可能：真·索引

本例没有，但要说清楚，免得混淆：

有些游戏不用指针，用 **"文本 ID → 字符串" 的索引表**（`u16`/`u32` 下标）。
那时改的是**下标值**，不是地址。识别方法：

- 表里的值**不是**任何字符串的 vaddr；
- 值是一串连续的小整数（`0,1,2,…` 或 `1000,1001,…`）；
- 改某个下标后，显示的内容变成**另一条已存在的文本**。

如果遇到这种情况，"改指针"和"改指令"都不适用，
要在**索引表**里换号 —— 这属于另一套体系，本文不展开。

## 7. 实操流程

### 7.1 前置：备份与回滚

```
layout.sprx.orig    ← 原始日版，只读
layout.sprx.work    ← 工作副本
```

本文所有改动都是**原地等长覆盖**，回滚 = 用 `.orig` 覆盖回去。
没有 code cave、没有插入、没有改头，所以不需要额外的撤销字节。

### 7.2 七步法

```
第 1 步  解析 PH，算出每段的 file↔vaddr 换算
         ↓
第 2 步  按 §4.5 的判据，确认本版里哪些 4 字节是指向文本的指针槽
         记下"槽 → 原串"的对应关系                   → slots_jp.txt
         ↓
第 3 步  按 §5.6 的判据，确认本版里哪些代码位置硬编码了文本地址
         记下"指令地址 → 原串"的对应关系             → code_jp.txt
         ↓
第 4 步  逐条翻译，按 §3.6 的规则决定"原地/搬走"
         优先原地（补 0），只有放不下才搬
         ↓
第 5 步  改完再核一遍：新旧两版按 file_offset 对齐，
         列出值变了的槽（就是需要写回的槽）           → slots_cn.txt
         ↓
第 6 步  对每个变了的槽，确认新值指向的串就是该槽的翻译
         确认无误后，把新 vaddr 小端写回
         ↓
第 7 步  对"搬走了的、且被代码硬编码引用"的串，改指令 imm
         ↓
         校验（§8）
```

> 第 2、3 步没有通用脚本可用 —— 段偏移、串池范围、槽位分布、
> 编译器怎么排指令，各版本都不一样。本文给的只是判据，
> 具体位置要按你自己手上的版本一条条确认。

### 7.3 第 6 步的判据（最容易出错的地方）

改完指针后，**必须做一次"反向验证"**：

```
对每一个槽 off：
    新值 v_new 指向的串  ==  该槽应该显示的翻译文本 ？
```

如果 `v_new` 指向的是**另一条不相干的串**，说明地址算错了（忘了减 0xA0？算错对齐？）。
这种错误在游戏里表现为"某个菜单项显示成别的菜单项的文字"，
不加验证很难发现，因为**不崩、不乱码，只是错**。

### 7.4 第 7 步的判据

只改**确实搬走了、且被指令直接引用**的串。

本例就是 `%s 他` → `%s 其他` 这 1 处。
另外 30 处硬编码的目标串都在原位，**不要动它们**——
动了就等于把本来正确的引用改坏。

## 8. 校验

### 8.1 字节级校验

```
差异字节 = 1,662
├─ 代码段    2   （1 段，1 条指令的 imm）
├─ 文本区 1,608   （74 段）
└─ 指针区    52   （13 段，13 个 u32）
```

三条加起来必须等于总数，**一段都不能多**。
如果多出来了，说明有地方被误改（比如把 `10 00 06 06` 这种头部改掉了）。

### 8.2 结构级校验

| 检查项 | 预期 |
|---|---|
| 文件大小 | 完全不变（1,250,156） |
| ELF 头 / Program Header | 0 字节差异 |
| `p_filesz` / `p_memsz` | 不变 |
| 每个指针槽的值 | 落在 `.rodata` 范围内 |
| 每个指针槽指向的串 | 是合法 UTF-8、以 `00` 结尾、长度 < 300 |
| 每个硬编码地址 | 同上 |

### 8.3 运行级校验

进游戏，逐项确认：

- 任务列表的**排序下拉**（登録順 / 名前順 / 同行回数順）三项都对
- 「はい / いいえ」确认框
- 多人同行时的「"%s 其他"」拼接显示（这是唯一改了指令的地方，**重点看**）
- 支援成员选择界面的长句（那段有 `\n` 换行，注意看有没有串行）

## 9. EBOOT.BIN：文本 + 指针，和 sprx 同一套做法

`EBOOT.BIN` 是**执行文件**，结构和 `layout.sprx` 完全同源（同样是 `e_type=0xFFA0` 的 PRX）。
两者是"主程序 + 一个依赖模块"的关系（§0.1）：机制共用一套，只是 EBOOT 里的数据比单个 sprx 更杂。

**它里面不只有代码 —— 需要翻的 UI 文本、指向这些文本的指针，一样都不少。**
机制和 §2 那三个热区完全一致（原地替换 / 搬走改指针 / 改指令里的地址），
只是规模小得多，排布上多了个"紧排区"。

此外还有一处和文本无关、但重新打包补丁就必须跟进的硬编码：
`PATCH.EDAT` 的大小校验值（§9.4）—— **这一处只有 PSP 版有，PSVita 没有**。

### 9.1 先看结构

Program Header 同样是 3 段（`e_phoff=0x34`）：

| 段 | p_offset | p_vaddr | filesz | flags |
|---|---|---|---|---|
| PH0 | `0x0000C0` | `0x000000` | `0x31A3C8` | RX |
| PH1 | `0x31A4C0` | `0x31A400` | `0x1449C` | RW |
| PH2 | `0x32E960` | — | `0xC6CA8` | 模块信息 |

换算同样是 `file = vaddr + 0xC0`（注意**不是** sprx 的 `+0xA0` —— 因为 PH 表长度不同）。

代码在 PH0 前段（`0x00C0`–`0x19F413`，约 1.6 MB），
`0x19F414` 往后的 1.5 MB 全是数据，**文本和指针都在这块里**。

### 9.2 文本在哪：PH0 数据区里的 UTF-8 串池

**编码同样是 UTF-8，一条串一个 `00` 结尾**，和 sprx 完全一样。
串池大致落在 vaddr `0x2D4000`–`0x2F6200`（file `0x2D40C0`–`0x2F62C0`），
玩家能看到的字集中在 `0x2DD000`–`0x2F1800` 这一段。

**统计**（`jp/EBOOT.BIN` → `cn/EBOOT.BIN`，PH0 全段可解码串）：

| 项 | 数量 |
|---|---|
| 串池里含假名的串 | **57 条** |
| 其中面向玩家、已翻译 | **35 条** |
| 其中 `!! Warning !!` / `!!! Error !!!` 调试串，保留原文 | **22 条** |

那 22 条不翻是**有意的**：它们全是不给玩家看的内部告警，例如

```
!! Warning !! : %s %d : %s : ヘアスタイルが定義域外です=>%d
!!! Error !!! : %s %d : %s : 親IDが設定されていません : karma_id = %d
```

翻它们没收益，还占地方。

**35 条里，33 条是原地替换，2 条必须改指针** —— 差别只在排布方式，和 §3.3 的段 A、§3.4 的段 B 是一回事。

#### 9.2.1 定长槽：中文短了，原地写 + 补 0

file `0x2DD0F8`（vaddr `0x2DD038`）：

```
日版  145 字节
      "アップデートデータが正常にインストール\nされていません。"
      "PlayStation®Networkで\n再ダウンロードしてください"
      占 0x2DD0F8..0x2DD189，下一条从 0x2DD18C 开始

繁中  69 字节
      "更新數據未正常安裝\n請在PlayStation®Network上重新下載"
      写在 0x2DD0F8..0x2DD13D，然后补 0 到 0x2DD18B
      下一条仍然从 0x2DD18C 开始
```

**偏移一个都没变，指针不用动。** 这就是 sprx 里段 A 的做法，在 EBOOT 里占了 33/35。

补零而不往前挤，原因和 §3.3 一样：这个位置可能被别的引用共享（同一条串被多处指向），
挤掉空隙就等于改了别人的起点。

### 9.3 指针：两张表，一共改了 3 个槽

EBOOT 的指针表不在数据段开头，而是夹在串池后面。按 §4.5 的判据在 PH0 里核，
本例能找到 **50 段**指针数组
（连续 4 项以上、每项都是指向串池的 vaddr），其中只有两张表在汉化里被动过：

| 表位置（vaddr） | 项数 | 改动项 |
|---|---|---|
| `0x2F6124` – `0x2F6148` | 10 | 1 项 |
| `0x30EFC4` – `0x30F084` | 49 | 2 项 |

为什么只有 3 个槽？因为**只有 2 条串的起点挪了位置** —— 它们恰好落在"紧排区"里。

#### 9.3.1 译文变短：后面的串整体前移

file `0x2E29F0`（vaddr `0x2E2930`）这一段是紧排的，串与串之间没有多余空隙：

```
日版  "よろしくお願いします"                 30 字节
      0x2E29F0..0x2E2A0D，\0 在 0x2E2A0E，对齐到 0x2E2A10
      下一条 "準備します" 在 vaddr 0x2E2950

繁中  "請多指教。"                           15 字节
      0x2E29F0..0x2E29FE，再补 12 个 00（到 0x2E2A0B）
      下一条 "我做個準備。" 落在 0x2E2A0C  → vaddr 0x2E294C（提前 4 字节）
```

于是表 `0x2F61EC` 的值要跟着改：

```
file 0x2F61EC (vaddr 0x2F612C)
  日版  50 29 2e 00  →  0x002E2950  "準備します"
  繁中  4c 29 2e 00  →  0x002E294C  "我做個準備。"
```

只改了 **1 个字节**：低字节 `50`→`4C`。高 16 位 `0x002E` 和次低字节 `0x29` 都没动 ——
差 4 而已，落在同一个 256 字节页里。

#### 9.3.2 译文变长 + 调了语序：后面的串后移

file `0x2F1800`（vaddr `0x2F1740`）：

```
日版  "確率で回復発動"                       21 字节
      0x2F1800..0x2F1814，\0 在 0x2F1815，对齐到 0x2F1818
繁中  "一定機率發動回復"                     24 字节
      0x2F1800..0x2F1817，\0 在 0x2F1818，对齐到 0x2F181C
```

后一条串因此从 vaddr `0x2F1758` 挪到 `0x2F175C`（**往后 4 字节**）。
而且这一条的译文还调了语序：

```
日版  "『リンクエイドした相手に\n90秒間、防御力アップ（小）付与』\nを習得しました"
      （宾语在前，动词"を習得しました"在最后）

繁中  "已習得\n『對連結救助的對象附加\n90秒內防禦力上昇（小）』"
      （动词提到最前）
```

语序一改，就没法在原位置"对齐写"了 —— 索性从新的起点重写。
所以这张表里有 **两个槽** 都指向它，都得改：

```
file 0x30F084 (vaddr 0x30EFC4)   日版 58 17 2f 00 → 0x002F1758
                                 繁中 5c 17 2f 00 → 0x002F175C
file 0x30F0AC (vaddr 0x30EFEC)   日版 58 17 2f 00 → 0x002F1758
                                 繁中 5c 17 2f 00 → 0x002F175C
```

**同一个目标串被几个槽指着，就得改几个槽** —— 判据同 §4.5：
只改你找到的第一个，另一处照样显示旧位置。

#### 9.3.3 怎么把 EBOOT 的指针槽找全

EBOOT 比 sprx 好找，因为串池只有一块：vaddr `0x2D4000`–`0x2F6200`，
指针槽全在串池之后的数据区里，而且**连成数组**：

```
vaddr 0x2F6124–0x2F6148    10 项
vaddr 0x30EFC4–0x30F084    49 项
```

做法：

1. 从串池末尾往后看，找**连续多个 4 字节值都落在串池范围**的地方 —— 那就是数组的起点；
2. 数组里每个值按 `+0xC0` 换算，都要能解出一条以 `00` 结尾的合法 UTF-8 串（判据见 §4.5）；
3. 改完串之后，把**数组里指向漂移串的每一项**都改掉。一个串被两个槽指着就改两个。

> **别在 `0x19F414` 之前的代码段里找指针**：那里的 u32 是指令，
> 读出来的值偶尔也会落进串池范围，会造出一堆假槽。
> 数据区里混着的字库二进制同样会误判，所以每一条都要确认目标确实是合法串。

### 9.4 代码段那 2 个字节：PATCH.EDAT 的大小校验（PSP 专有）

> **这一处只在 PSP 版存在，PSVita 版没有** —— PSVita 那边不需要改任何"文件大小常量"，
> 改完文本和指针就可以直接打包（详见 §10.4）。

日版和汉化版 A（`cn/bin/EBOOT.BIN`）在这段代码上的区别只有 2 个字节：

```
日版  0003BA70  E9 17 03 3C   lui   $v1, 0x17E9
      0003BA74  2E 00 05 3C   lui   $a1, 0x002E
      0003BA78  2F 00 07 3C   lui   $a3, 0x002F
      0003BA7C  00 38 63 34   ori   $v1, $v1, 0x3800    → 0x17E93800

繁中  0003BA70  F2 17 03 3C   lui   $v1, 0x17F2
      0003BA74  2E 00 05 3C   lui   $a1, 0x002E
      0003BA78  2F 00 07 3C   lui   $a3, 0x002F
      0003BA7C  00 50 63 34   ori   $v1, $v1, 0x5000    → 0x17F25000
```

注意**这两条指令不相邻**：`lui $v1` 在 `0x03BA70`，`ori $v1` 在 `0x03BA7C`，
中间隔着两条构造别的地址的 `lui`（`0x2E0000`、`0x2F0000`）。
所以字节差异只有 **2 个**：`0x03BA70` 的 `E9`→`F2`、`0x03BA7D` 的 `38`→`50`（日版 → 汉化版 A）。

**这里改的不是地址，是一个 32 位无符号整数 —— `PATCH.EDAT` 的预期文件大小。**
游戏加载补丁容器前会拿实际文件长度跟它比对，**对不上就弹窗报错、拒绝加载**。
所以只要重新打包过 `PATCH.EDAT`，这两处立即数必须跟着改。

同一个项目、同一个位置，不同打包版本的值都不一样：

| 版本 | `lui` @ `0x03BA70` | `ori` @ `0x03BA7C` | 合并值 |
|---|---|---|---|
| 日版原版 | `0x17E9` | `0x3800` | `0x17E93800` |
| 汉化版 A | `0x17F2` | `0x5000` | `0x17F25000` |
| 汉化版 B | `0x17F2` | `0xA000` | `0x17F2A000` |

日版→汉化版 A 连 `lui` 都变了（跨了 64KB 边界），汉化版 A→B 只动了 `ori`。
**值完全跟着打包结果走，照抄别人的成品一定出错。**

#### 9.4.1 怎么算出自己的新值

设重打包后的 `PATCH.EDAT` 大小为 `N`：

```
hi = N >> 16
lo = N & 0xFFFF
写入  lui $v1, hi ；ori $v1, $v1, lo
```

`N` 是 32 位无符号整数（`0`–`0xFFFFFFFF`）。本作补丁约 383 MB，`hi = 0x17F2`；
如果换成小体量补丁、`N < 0x10000`，`hi` 就是 0，照写 `lui $v1, 0x0000` 即可，
不要去改成别的写法。

编码公式（小端存放，`imm` 指 16 位立即数）：

| 指令 | 机器码 | 文件里存的字节 |
|---|---|---|
| `lui $v1, imm` | `0x3C030000 \| imm` | `imm` 低字节在前，再 `03 3C` |
| `ori $v1, $v1, imm` | `0x34630000 \| imm` | `imm` 低字节在前，再 `63 34` |

代入上面的值，得到该写进文件的字节：

```
lui $v1, 0x17E9   → 0x3C0317E9 → E9 17 03 3C   ✓ 日版
ori $v1,$v1,0x3800 → 0x34633800 → 00 38 63 34  ✓ 日版
lui $v1, 0x17F2   → 0x3C0317F2 → F2 17 03 3C   ✓ 汉化版 A / B（两版相同）
ori $v1,$v1,0x5000 → 0x34635000 → 00 50 63 34  ✓ 汉化版 A
ori $v1,$v1,0xA000 → 0x3463A000 → 00 A0 63 34  ✓ 汉化版 B
```

- 日版 → 汉化版 A：改 **2 个字节**（`0x03BA70` 的 `E9`→`F2`、`0x03BA7D` 的 `38`→`50`）
- 汉化版 A → 汉化版 B：只改 **1 个字节**（`0x03BA7D` 的 `50`→`A0`）

其余字节（两条指令的 opcode/寄存器号 + 中间那两条 `lui`）一个都不用动。

#### 9.4.2 两个坑

**坑 1：`ori` 是零扩展，`addiu` 是有符号 —— 别搞混。**

本例用的是 `ori`，所以 `0x3800`、`0x5000` 直接拼，不用管符号。
但如果你的版本里这两条是 `lui` + `addiu`，那么 `lo ≥ 0x8000` 时：

```
不能写  addiu $v1,$v1,0x9000
要写    addiu $v1,$v1,0x9000-0x10000 = -0x7000   ，同时 hi 要 +1
```

否则拼出来的值会差 `0x10000`，症状就是"明明大小算对了还是弹窗"。

**坑 2：`lui` 的立即数也要跟着改。**

`0x17E9` → `0x17F2` 就是高 16 位变了。这一处最容易漏 ——
只改 `ori` 的话，值变成 `0x17E95000`，照样弹窗。

#### 9.4.3 定位与验证

**定位**（按可靠性排序）：

1. 直接搜 `lui` 的字节序列 `E9 17 03 3C`（日版原样）→ 命中 `0x03BA70`；
   再搜 `ori` 的 `00 38 63 34` → 命中 `0x03BA7C`
   （**别把这两串当成连续 8 字节搜** —— 它们中间隔着两条 `lui`）
2. 先量自己 `PATCH.EDAT` 的大小算出 `lui`/`ori` 的 word，再分别搜这两个 word
3. 搜 ASCII `PATCH.EDAT`，同一区块里就有 `src/fw/res_patch.c` 的报错模板；
   整个文件里这个常量只有一处，不用再找第二处

> **别只按立即数搜。** 汉化版 A 里 `ori $v1, $v1, 0x5000` 出现了 **2 次**：
> `0x03BA7C`（要改的这个）和 `0x030B4C`。后者配的是 `lui $v1, 0x0020`，
> 合起来是 `0x00205000`，跟文件大小毫无关系。
> **必须拿 `lui` + `ori` 的配对结果去比，不能单看低 16 位。**

**改完怎么确认**：

- 进游戏，补丁内容正常加载、不弹窗 → 通过
- 仍然弹窗 → 先量一遍当前 `PATCH.EDAT` 的实际字节数，看是不是等于你填的 `N`；
  再检查 `lui` 和 `ori` 是不是**两个都**改了

> 这一步和 §5 的"改指令 imm"是同一套手艺（`lui` + 低 16 位指令两步构造 32 位值），
> 但改的东西不同：**§5 改的是地址，这里改的是数值本身。**
> 相同的是，两者都只能原地改立即数字节，`lui` 的高 16 位必须跟着一起动。

### 9.5 结论：两个文件，同一套做法

| 文件 | 文本在哪 | 指针在哪 | 数量级 |
|---|---|---|---|
| `bin/*.sprx` | PH0 尾部 `.rodata`（`0x0F14F0`–`0x0F4E81`） | PH1 数据段（`0x10F4DC`–`0x10F95C`） | 600+ 条串 / 13 个指针槽 |
| `EBOOT.BIN` | PH0 数据区串池（vaddr `0x2D4000`–`0x2F6200`） | 串池后的指针数组（`0x2F6124`、`0x30EFC4` 两张） | 57 条日文串 / 3 个指针槽 |

**PSP 的 EBOOT 还有一处 sprx 没有、PSVita 也没有的硬编码**：
`PATCH.EDAT` 的大小校验值（§9.4）。这是 PSP 这套补丁加密容器特有的产物，
移植到 PSVita 时**不用找、也不用改**（§10.4）。

**做法上没有区别**：

1. 先按 UTF-8 把串认出来，**原地替换 + 补 0**，偏移不变就不用管指针
2. 串在紧排区、长度变了、或者译文调了语序 → 起点会挪，**改所有指向它的槽**
3. 改槽之前先按 §4.5 的判据核一遍，同一个目标可能被好几个槽指着（§9.3.2 那两个）

> **两者的骨架是同一套**：ELF32 小端 MIPS、3 个 Program Header，
> "文本在 `.rodata`、指针在数据段"这个模型也一致。
> 唯一必须先确认的差别是换算基准：sprx 是 `+0xA0`，EBOOT 是 `+0xC0`。
> 换成别的版本时，这个差值照样要按 PH 表重新算，不能套用。

## 10. PSVita：先脱壳，方法不变

前面九章讲的都是 PSP（MIPS）。**PSVita 版的翻法完全一致**，
差别只有四处：**动手前必须先脱壳**（PSP 的 `EBOOT.BIN` / `.prx` 本身就是 ELF，
PSVita 的 `eboot.bin` / `.self` 外面套着一层 SELF，里面的段还可能压过）、
指令集从 MIPS 换成 **ARMv7-A**、
换算基准不一样（vaddr 从 `0x81000000` 起算）、
以及 §9.4 那个 `PATCH.EDAT` 大小校验**在 PSVita 上根本不存在**（§10.4）。

### 10.1 文件对应关系

| | PSP | PSVita |
|---|---|---|
| 执行文件 | `EBOOT.BIN` | `eboot.bin` |
| 依赖模块 | `.prx` / `.sprx` | `.self` |
| 文件外层 | PRX（`\x7fELF` + `e_type=0xFFA0`）—— **本身就是 ELF** | **SELF**（`SCE\0` 头 + 内层 ELF）—— **不是 ELF** |
| 文件里的段 | 明文 | **可能被 zlib 压缩**（本样本的 `eboot.bin` 就是） |
| 改之前 | 直接打开改 | **FAGDec 解密脱壳成 ELF** |
| 收工之后 | 直接放回 | **vita-elf-inject 注回 `eboot.bin`** |
| 架构 | MIPS（`e_machine=0x08`） | **ARMv7-A**（`e_machine=0x28`） |
| `e_type` | `0xFFA0`（PRX） | `0xFE04`（脱壳后的 ELF） |
| 节表 | 无（`e_shoff=0`） | 无（`e_shoff=0`） |

本节用两份实测样本，一份主程序、一份模块：

| 样本 | 大小 | 用途 |
|---|---|---|
| `eboot.bin`（SELF） | 1,870,804（`0x1C8BD4`） | 讲脱壳：段是压缩的 |
| `eboot.bin.elf`（FAGDec 输出） | 4,705,768（`0x47CDE8`） | 讲 ELF 结构、换算 |
| `god_m001_Title.self`（模块） | 623,700（`0x98454`） | 讲文本与指针（段未压缩，内容能直接看见） |

换到别的模块，数值都会变，判据不变。

### 10.1.1 流程：FAGDec 脱壳 → 改 ELF → vita-elf-inject 注回

**PSP 的 `EBOOT.BIN` 和 `.prx` 打开就是 ELF，PSVita 的不是。**
`eboot.bin`、`.self` 都是 SELF 容器 —— 真正的 ELF 被封在壳里，壳带签名，
里面的段还可能压过。所以动手之前的第一步永远是**脱壳**：

```
eboot.bin / xxx.self            ← 游戏里那份（SELF 容器）
        │  FAGDec 解密脱壳
        ▼
eboot.bin.elf / xxx.elf         ← 完整 ELF，翻译就以它为基础
        │  按 §3–§5 改文本、改指针、改指令
        ▼
改好的 ELF
        │  vita-elf-inject 注入回 eboot.bin
        ▼
新的 eboot.bin                  ← 放回游戏（真机需绕过签名校验）
```

`*.self` 模块走的是同一条流程，FAGDec 一样吃得下 ——
只是输出文件名不同（`xxx.self` → `xxx.elf`），后面的步骤一个字都不用改。

**中间这一步确立了唯一的基准**：往后所有偏移、所有地址换算，
全部相对**脱壳出的 ELF** 来算，不再相对 SELF（§10.1.4）。

#### 为什么必须用 FAGDec，不能手工截掉 `0x1000`

因为段可能是**压缩**的。本样本 `eboot.bin` 的实测：

```
SELF 大小       0x1C8BD4   (1,870,804)
ELF  大小       0x47CDE8   (4,705,768)   ← 解压后，比 SELF 还大 2.5 倍
SELF 0x10E0 处  78 9C      ← zlib 头（默认压缩级别）
```

`0x10E0` 是 PH0 在 SELF 里的起点。那里不是代码，是 zlib 流的头两个字节。
把这段 zlib 解出来，头 8 个字节是：

```
解压结果前 8 字节   f0 43 2d e9 14 d0 4d e2
ELF 0x00E0 处       f0 43 2d e9 14 d0 4d e2   ← 完全一致
```

也就是说：**ELF 里的段 = SELF 里对应段解压后的结果**，而且压缩前后大小差得很远：

| 段 | SELF 里（压缩后） | ELF 里（解压后） | 倍数 |
|---|---|---|---|
| PH0（代码 + 只读数据） | `0x19FEF7` | `0x3FEF68` | 2.46× |
| PH1（可写数据） | `0x004F13` | `0x01FCAC` | 6.43× |
| PH2 | `0x01F8E3` | `0x05273C` | 2.61× |
| PH3 | `0x0032B4` | `0x009BD8` | 3.07× |
| PH4 | `0x000121` | `0x001DC4` | 26.37× |

每段"在 SELF 里从哪开始、压完剩多少"，都记在 SELF 头的 **section info 表**里
（`0x180` 起，每项 `0x20` 字节，顺序与 ELF 的 PH 索引一一对应）：

| 项 | SELF 内偏移 | 压缩后大小 | 解压后头 4 字节 | 对应 |
|---|---|---|---|---|
| `[0]` | `0x000010E0` | `0x19FEF7` | `f0 43 2d e9` | PH0（ELF `0xE0`） |
| `[1]` | `0x001A0FE0` | `0x004F13` | `47 58 50 00` | PH1（ELF `0x3FF050`，GXP） |
| `[2]` | `0x001A6030` | `0x01F8E3` | `00 2B C0 22` | PH2（ELF `0x420AD0`） |
| `[3]` | `0x001C5920` | `0x0032B4` | `11 02 81 DF` | PH3（ELF `0x473210`） |
| `[4]` | `0x001A5F00` | `0x000121` | `12 63 72 74` | PH4（ELF `0x41ED00`） |

五项全部以 `78 9C` 开头 —— 这个 eboot 的**每一段都压过**。
注意 SELF 内偏移**不是按顺序排的**（`[4]` 在 `0x1A5F00`，比 `[2]` 的 `0x1A6030` 还靠前），
所以别拿"偏移顺序"去推段号。

**交叉验证的办法**：把 section info 每一项解压、取头 4 字节，和 ELF 里对应段的头 4 字节比。
对上了，说明脱壳结果正确；对不上，说明段号或基准搞错了。这是最省事的一步自检。

所以：

- **手工 `dd skip=4096` 只能得到一堆 zlib 流**，改它毫无意义（改的是压缩数据，不是文本）。
- 手工算偏移也全部作废 —— SELF 里 PH1 在 `0x1A0FE0`，ELF 里却在 `0x3FF050`，
  中间隔着解压后的膨胀量，不是固定差值。
- FAGDec 做的事就是"解 SELF 头 + 逐段解压 + 重排成标准 ELF"，
  输出的大小正好等于 SELF 头里记的 `elf_filesize`（本样本 `0x47CDE8` ✓）。

> **也有不压缩的情况**：`god_m001_Title.self`（标题界面模块）的段就是明文，
> `0x10E0` 处直接是 Thumb 代码 `2d e9 f0 49`，脱壳结果就是 SELF 去掉 `0x1000` 头、
> 逐字节相同（619,604 字节）。
> **但你不能靠"看字节像不像代码"来决定要不要解压** —— 一律交给 FAGDec，
> 它对这两种情况都输出正确的 ELF。这就是工具存在的理由。

### 10.1.2 被脱掉的那层壳长什么样

知道壳的结构，是为了判断"脱干净了没有"、以及"注回时哪几个字段会被重新填"。
本样本 `eboot.bin` 的 SELF 头，前 `0x1000` 字节：

```
0x0000  SCE 头（0x80 字节）
0x0080  appinfo（0x20 字节：authid / vendor_id / self_type / version）
0x00A0  ELF 头「副本」（0x34 字节）        ← 不是真 ELF，只是头的一份拷件
0x00E0  程序头「副本」（5 × 0x20）        ← 同上
0x0180  section info（5 × 0x20）          ← 每段在 SELF 里的位置、压缩后大小
0x0220  sceversion
0x0230  control info（0x2C0 字节）        ← 签名 / digest
0x1000  ← 内层 ELF 真正开始的地方
```

SCE 头字段（小端）：

| 偏移 | 字段 | 本样本值 | 含义 |
|---|---|---|---|
| `0x00` | magic | `53 43 45 00` | `SCE\0` |
| `0x04` | version | 3 | |
| `0x08` | sdk_type | `0x00C0` | |
| `0x0A` | header_type | **1** | SELF |
| `0x0C` | metadata_offset | `0x600` | |
| `0x10` | **header_len** | **`0x1000`** | 头部总长，也是内层 ELF 的起始位置 |
| `0x18` | **elf_filesize** | **`0x47CDE8`** | **脱壳后** ELF 的大小（解压后） |
| `0x20` | self_filesize | `0x1C8BD4` | 文件本身的大小（压缩后） |
| `0x38` | appinfo_offset | `0x80` | |
| `0x40` | elf_offset | **`0xA0`** | ELF 头「副本」位置 |
| `0x48` | phdr_offset | **`0xE0`** | 程序头「副本」位置 |
| `0x50` | shdr_offset | `0` | 没有节表 |
| `0x58` | section_info_offset | `0x180` | |
| `0x60` | sceversion_offset | `0x220` | |
| `0x68` | controlinfo_offset / size | `0x230` / `0x2C0` | 签名等信息 |

> **`elf_filesize` 和 `self_filesize` 一般不等** ——
> 前者是解压后的 ELF（`0x47CDE8`），后者是磁盘上的 SELF（`0x1C8BD4`），
> 两者差了 2.5 倍。脱壳出来的 ELF 大小必须等于 `elf_filesize`，这是第一个自检点。
>
> 段未压缩时（`god_m001_Title.self`）才会出现 `elf_filesize + header_len = self_filesize`
> 这种巧合关系（`0x97454 + 0x1000 = 0x98454`）—— **别把它当通用公式**。

> `0xA0` 和 `0xE0` 那两份是**头的副本**，方便加载器和识别工具快速拿到程序头，
> 不是"ELF 从这里开始"。真 ELF 在 `0x1000`。把 `0xA0` 当成 ELF 起点去算偏移，
> 得到的每个地址都会偏，症状是"改了没反应"或"改坏了别的字节"。

### 10.1.3 脱壳后得到的是标准 ELF，5 个段

`eboot.bin.elf` 的头（`4,705,768` 字节）：

```
7f 45 4c 46 01 01 01 00   e_type=0xFE04  e_machine=0x28(ARM)   e_entry=0x00329C20
e_phoff=0x34  e_shoff=0  e_phnum=5  e_phentsize=0x20  e_flags=0x05000000
```

5 段全部落在文件内：

| 段 | p_type | p_offset | vaddr | filesz | memsz | 权限 | 说明 |
|---|---|---|---|---|---|---|---|
| PH0 | `1` PT_LOAD | `0x000000E0` | `0x81000000` | `0x3FEF68` | `0x3FEF68` | R-X | 代码 + 只读数据（约 4 MB） |
| PH1 | `1` PT_LOAD | `0x003FF050` | `0x813FF000` | `0x01FCAC` | `0x049934` | RW- | 可写数据 |
| PH4 | `0x6FFFFF01` | `0x0041ED00` | 0 | `0x001DC4` | 0 | — | 模块信息 |
| PH2 | `0x60000000` | `0x00420AD0` | 0 | `0x05273C` | 0 | — | 重定位 |
| PH3 | `0x60000000` | `0x00473210` | 0 | `0x009BD8` | 0 | — | 重定位 |

按文件偏移排是 PH0 → PH1 → PH4 → PH2 → PH3，**段与段之间没有空洞**：

```
0x00E0 + 0x3FEF68 = 0x3FF048   → 空 8 字节    → 0x3FF050  PH1
0x3FF050 + 0x1FCAC = 0x41ECFC  → 空 4 字节    → 0x41ED00  PH4
0x41ED00 + 0x1DC4 = 0x420AC4   → 空 12 字节   → 0x420AD0  PH2
0x420AD0 + 0x5273C = 0x47320C  → 空 4 字节    → 0x473210  PH3
0x473210 + 0x9BD8 = 0x47CDE8   ← 正好是文件尾，与 SCE 头里的 elf_filesize 相等
```

> **这就是脱壳之后该看到的东西**：`\x7fELF` 在文件第 0 字节、`e_shoff=0`、
> 5 个段首尾相接铺满全文件、末尾对齐 `elf_filesize`。脱出来的 ELF 不满足这几条，先别急着改。
>
> **段之间那几个 4–12 字节的小空隙**是 `p_align=0x10` 的对齐填充，全零。
> 想给译文找地方时它们也算候选，但通常太小（§6）。

段数据是**明文**（这是解压后的结果，不是 SELF 里的压缩态）：
`0xE0` 处就是 ARM 代码 `f0 43 2d e9`（从 `0xE2` 起才是指令 `2d e9 f0 43` = `push.w {r4-r9, lr}`），
`0x380000` 附近是编译进来的 Lua 运行时字符串（`loop in gettable`、`__persist`…），
`0x3FF050`（PH1 起点）是 `GXP\0` 开头的子容器。

> PH1 的 `memsz` 比 `filesz` 大 `0x49C88` —— 多出来的部分是 `.bss`，加载时才分配，文件里没有。
> 改数据只能改 `0x003FF050 .. 0x0041ECFC` 这 `0x1FCAC` 字节。

### 10.1.4 换算公式：以脱壳后的 ELF 为基准

```
file = p_offset + (vaddr − p_vaddr)
```

两段分别代入：

```
PH0（代码 + 只读数据）  file = 0x00E0   + (vaddr − 0x81000000)
PH1（可写数据）        file = 0x3FF050 + (vaddr − 0x813FF000)
```

以模块样本验证（`god_m001_Title` 的串池，同一套公式）：
`vaddr 0x81049E9C` → `0xE0 + 0x49E9C = 0x49F7C`，
那里正是串 `"移行するデータの選択"` 的起点（30 字节）。

> **和 PSP 的差别只在 vaddr 基点**：PSP 的 vaddr 从 `0` 起，`file = vaddr + 0xA0`；
> PSVita 的 vaddr 从 `0x81000000`（主程序）/ `0x813FF000`（数据段）这类高地址起，
> 套用 PSP 的 `+0xA0` 算出来会全错。
>
> **基准错了的症状**：拿 SELF 的偏移去查 ELF，或者反过来 —— 前者落在压缩流里，
> 后者越界。改完进游戏毫无反应，或者干脆启动失败，都要先回头核这个基准。

### 10.1.5 文本在哪：不是每个可执行文件都装着文本

先看 `eboot.bin.elf` 这个主程序的实测：

| 项 | 实测结果 |
|---|---|
| 含日文的 UTF-8 串（连续假名 / CJK） | **0 条** |
| 能看懂的 ASCII 串 | 3,861 条，全是 `SceAppUtil`、`SceAudio` 这类系统库名，和 Lua 运行时内部提示 |
| PH0 尾部 `0x380000` 附近 | Lua 解释器字符串（`loop in gettable`、`__persist`…） |
| PH1（`0x3FF050` 起，`0x1FCAC` 字节） | **195 个 `GXP\0` 子容器**，UI 部件定义，字段名是 `alpha` / `textureFore` / `position` 这类英文 |

也就是说：**这个主程序里没有可翻译的 UI 文案**，装的是代码、Lua 运行时、
和 195 段 UI 部件定义（GXP）。文本在资源包（`.rdp` / `.res` / `files.tr2`）
和各界面模块（`.self`）里。

> 这不是"找错了"。主程序往往只做调度，一开始就在 `eboot.bin` 里翻文本，
> 有可能第一步就发现"没得翻"—— 这是正常结果，说明该去翻模块和资源包了。
> 但流程不变：真要在 `eboot.bin` 里改东西（比如它自己也带一段界面文案），
> 用的还是下面这套「脱壳 → 改 → 注回」。

真正装文本的是模块。模块样本 `god_m001_Title`（`*.self`，同一套脱壳流程）的实测：

| 项 | 实测（脱壳后的 ELF 内偏移） |
|---|---|
| 含多字节字符（日文/汉字）的 UTF-8 串 | 1,599 条 |
| 串池起点（最好上手的入口） | `0x049F7C`（vaddr `0x81049E9C`） |
| 串池末端 | 约 `0x059266` |
| PH1 里指向 PH0 串池的合法 u32 槽 | 2,573 个 |
| 其中连续 4 项以上的指针数组 | 20 段 |
| 最集中的一张表 | `0x0604F0`–`0x060600`，界面文案 |

找法与判据和 PSP 完全一样（§4.5 的四条），只是把"值落在 `.rodata` vaddr 范围"换成
"值落在 `0x81000000 ~ 0x81000000 + PH0.filesz`"。

一条串被多个槽指着是常态，改前先把所有指向它的槽找全：

| 串 | vaddr | 指向它的槽（脱壳 ELF 内） |
|---|---|---|
| `移行するデータの選択` | `0x81049E9C` | `0x0604F0`、`0x060504`、`0x06051C` |
| `【PSP®】GOD EATER BURST` | `0x8104A154` | `0x060588`、`0x060590`、`0x060594` |

### 10.2 文本层：一条判据都不用改

| 环节 | 结论 |
|---|---|
| 编码 | 仍是 **UTF-8**，一条串一个 `00` 结尾，补 0 到 4 字节对齐 |
| 文本位置 | 仍在只读段（PH0 后段）的串池里，形态与 §3.2 的段 A / 段 B 相同 |
| 指针 | 仍是 4 字节小端 **vaddr**，不是文件偏移、不是索引；但高位是 `0x81`（本样本 `0x81000000` 起），不是 PSP 那种 `0x000Fxxxx` |
| 中文短了 | 原地写 + 补 0，后面的串一个都不许挤（§3.3） |
| 中文长了 / 调语序 | 搬走，然后改所有指向它的引用（§3.5、§4） |
| 重定位 | 指针存 vaddr，加载时加基址 —— 改指针不破坏重定位（§4.2） |
| 换算 | `file = p_offset + (vaddr − p_vaddr)`，**不是** `vaddr + 0xA0`；全部按脱壳后的 ELF 算（§10.1.4） |

**唯一要换的是"指令里那个地址长什么样"。**

### 10.3 指令层：`lui`+`ori` 在 ARMv7-A 上有两种形态

**形态一：`movw` + `movt`** —— 和 §5 完全对应，直接照做。
模块样本 `god_m001_Title` 启动时取 PH1 数据段基址，就是这一对（反汇编脱壳后的 ELF）：

```
0x81000046:  movw  r0, #0x1000        ; 低 16 位
0x8100004A:  movt  r0, #0x8106        ; 高 16 位   →  0x81061000
```

改法：`新值 & 0xFFFF` 写进 `movw`，`新值 >> 16` 写进 `movt`。
**两条都是零扩展**，没有 `addiu` 那个"`0x8000` 边界要进位"的坑 —— 这一点比 MIPS 简单。

**形态二：`ldr` + 字面量池** —— 更常见，而且**它其实更像 §4，不是 §5**：

```
ldr   r0, [pc, #0x14]     ; 从 PC+0x14 读 4 字节
...
.word 0x81049E9C          ; ← 地址在这里，指令里根本没有
```

指令里的 `#0x14` 只是"池子离 PC 多远"，改地址要改池里那个 `.word`（4 字节），
**不要照着 §5 去改 `ldr` 的偏移值** —— 那不是地址，改了只会读错位置。
池里那个 `.word` 里放的同样是 **vaddr**，所以改法跟改数据段的指针槽是一回事。

怎么认：`ldr` 的偏移落在本函数末尾附近，该处 4 字节的值恰好在只读段范围内、
且换算后指向合法 UTF-8 串 —— 与 §4.5 判指针槽的四条判据是同一套。

**还有一点：Thumb-2 是可变长指令**（2 字节与 4 字节混排）。
ARM 模式下代码 4 字节定长，可以按 4 字节步进扫；
Thumb-2 下不能假设步进，否则会把半条指令当成一条来解。

两个样本的代码都是 Thumb-2，形态还不一样：

- 模块 `god_m001_Title`：PH0 起点（脱壳 ELF 的 `0xE0`）就是指令边界，`2d e9 f0 49`
  = `push.w {r4-r8, lr}`（4 字节），紧跟的 `2d ed 02 8a` 也是 4 字节。
- 主程序 `eboot.bin`：`0xE0` 处是 `f0 43 2d e9`，**真指令从 `0xE2` 才开始**
  （`2d e9 f0 43` = `push.w {r4-r9, lr}`）—— 前面那 2 字节是上一段的尾巴/填充。

这就是"不能按固定步长扫"的实证：同是 Thumb-2，段起点未必对齐指令边界。
从 `e_entry`（本样本 `0x00329C20`）或反汇编器自动定位的函数起点进入才可靠。

### 10.4 PSP 独有的那处校验，PSVita 没有

§9.4 讲的 `PATCH.EDAT` 大小校验，是 **PSP 补丁容器**的产物：
PSP 的更新补丁被打包成一个 `PATCH.EDAT`，主程序在加载前先比对它的实际字节数
是不是自己编译期记下的那个值，对不上就弹窗、拒绝加载。

**PSVita 的更新补丁不是这个形态** —— 没有 `PATCH.EDAT` 这个容器，
也没有"把大小写死在执行文件里、加载前比对"这套逻辑。所以：

| | PSP | PSVita |
|---|---|---|
| `PATCH.EDAT` 大小校验 | **有**，写在 `EBOOT.BIN` 代码段（§9.4） | **无** |
| 重新打包补丁后要改代码吗 | 要，改 `lui` + `ori` 两处立即数 | **不用** |
| 忘改的症状 | 进游戏弹窗报错、补丁不加载 | 不存在这个问题 |

> 也就是说，PSVita 版做完 §3–§5 那三件事（文本、指针、指令里的地址）、
> 再用 vita-elf-inject 注回 `eboot.bin`，就可以收工，
> **不需要再去代码段里找任何"文件大小"类的常量**。
>
> 反过来说，PSP 版如果只改了文本和指针、漏了这一处，前面做得再对也进不去游戏 ——
> 这是两版之间唯一一处"PSP 要多做一步"的地方。

### 10.5 小结

| | PSP（MIPS） | PSVita（ARMv7-A） |
|---|---|---|
| 执行文件 | `EBOOT.BIN` | `eboot.bin`（SELF 壳） |
| 依赖模块 | `.prx` / `.sprx` | `.self`（SELF 壳） |
| 动手前 | 无（本身就是 ELF） | **FAGDec 脱壳出 ELF**（§10.1.1） |
| 收工后 | 直接放回 | **vita-elf-inject 注回 eboot.bin**（§10.1.1） |
| 文本 | UTF-8 串池 + 指针表 | **同** |
| 引用在数据里 | 改 u32 槽 | **同** |
| 引用在指令里 | `lui` + `addiu`/`ori` | `movw` + `movt`，或改字面量池的 `.word` |
| 立即数符号 | `addiu` 有符号 | `movw`/`movt` 零扩展 |
| 段内换算 | `file = vaddr + (p_offset − p_vaddr)`，本例 `+0xA0` / `+0xC0` | `file = p_offset + (vaddr − p_vaddr)`，本例 PH0 `0xE0`、PH1 `0x3FF050`（§10.1.4） |
| 段数据 | 明文 | **SELF 里可能 zlib 压缩**（`eboot.bin` 是），脱壳后才是明文 |
| `PATCH.EDAT` 大小校验 | **有**（§9.4） | **无**（§10.4） |
| 加载前 | 无（PRX 直接加载） | 改完签名对不上，真机需跳过校验（打包环节，不在文本层） |

> 所以 §11 速查表里那些判据，PSVita 一样能用；
> 只有"代码里的地址怎么改"那一行，把 `lui`/`addiu` 换成 `movw`/`movt` 或字面量池。

## 11. 速查

| 问题 | 答案 |
|---|---|
| 这文件是什么 | ELF32 小端的 SCE PRX（`e_type=0xFFA0`，MIPS） |
| `EBOOT.BIN` / `.prx` / `.sprx` 什么关系 | `EBOOT.BIN` 是执行文件，`.prx` 是依赖模块，`.sprx` 是**更新补丁里的同名模块**，与 `.prx` 同构（§0.1） |
| 那改哪个 | 改补丁里实际生效的那份；原版镜像里的可能被补丁覆盖 |
| PSVita 版呢 | `eboot.bin` + `.self` 依赖模块，两者都是「SELF 头 + 内层 ELF」；**先 FAGDec 脱壳成 ELF**，改完 vita-elf-inject 注回；文本/指针判据不变，指令集换 ARMv7-A（§10） |
| 有节表吗 | 没有（`e_shoff=0`）；PSVita 脱壳出的 ELF 也是 `e_shoff=0`，只能靠程序头划范围 |
| 文本在哪 | PH0 尾部 `.rodata`，`0x0F14F0`–`0x0F4E81` |
| 指针在哪 | PH1 数据段，`0x10F4DC`–`0x10F95C`，每 4 字节一个 |
| 编码 | **UTF-8**（日版繁中版一致，**不存在 Shift-JIS**）；汉字/假名都是 3 字节 |
| 字符串结尾 | `00`，然后补 0 到 **4 字节对齐** |
| `file_offset` 怎么算 | PSP：`vaddr + (p_offset − p_vaddr)`，本例两段都是 `+0xA0`（EBOOT 是 `+0xC0`），别处要分别算 |
| PSVita 的 `file_offset` 怎么算 | `p_offset + (vaddr − p_vaddr)`，**按脱壳后的 ELF 算**；vaddr 从 `0x81000000` 起，PH0 落 `0xE0`、PH1 落 `0x3FF050`。**不要套 PSP 的 `+0xA0`**（§10.1.4） |
| 中文比日文长怎么办 | 搬到空闲区/空洞，然后**改所有指向它的指针** |
| 中文比日文短怎么办 | 原地写 + 补 0，**不要**把后面的串往前挤 |
| 指针值是什么 | **vaddr**（不是 file offset，不是索引），小端 u32 |
| 改指针会破坏重定位吗 | 不会。PRX 是加性重定位，`值 += base` |
| 代码里的地址怎么改 | 改 `addiu`/`ori` 的 imm（2 字节）；跨 64KB 连 `lui` 一起改 |
| `addiu` 的 imm 要注意 | **有符号** 16 位；`ori` 是零扩展 |
| PSVita 的代码地址怎么改 | `movw` 填低 16 位、`movt` 填高 16 位（都零扩展）；或改 `ldr` 所指字面量池里的 `.word`（§10.3） |
| 怎么认指针槽 | 4 字节对齐、值落在 `.rodata` 内、换算后指向合法 UTF-8 串（判据见 §4.5） |
| 怎么认代码里的地址 | `lui` + `addiu`/`ori` 同一寄存器配对，拼出的值落在 `.rodata`（判据见 §5.6） |
| `EBOOT.BIN` 里也有 UI 文本吗 | **有**，在 PH0 数据区的串池里，vaddr `0x2D4000`–`0x2F6200` |
| `EBOOT.BIN` 的文本有多少 | 含假名的串 57 条：35 条面向玩家的已译，22 条 `!! Warning !!` 调试串保留原文 |
| `EBOOT.BIN` 的指针在哪 | 串池后的指针数组，`0x2F6124`–`0x2F6148`（10 项）、`0x30EFC4`–`0x30F084`（49 项）；本次只改 3 个槽 |
| 为什么 `EBOOT.BIN` 要改指针 | 紧排区里一条串变长/变短，后面的串整体漂移；译文调语序也要换起点 |
| 重打包了 `PATCH.EDAT` 要改哪 | `EBOOT.BIN` 的 `0x03BA70`（`lui`）和 `0x03BA7C`（`ori`），填新文件大小；**每次打包值都不同，不能照抄** |
| 改错 `PATCH.EDAT` 大小什么症状 | 进游戏弹窗报错，补丁不加载（`src/fw/res_patch.c` 那套校验） |
| PSVita 也要改这个校验值吗 | **不用**。`PATCH.EDAT` 大小校验只有 PSP 版有，PSVita 没有这个容器（§10.4） |
| 本文改了多少 | 代码 2 字节（1 处）+ 指针 52 字节（13 处）+ 文本 1,608 字节 |
| 怎么确认没改坏 | 差异字节 1,662 要能拆成 2 + 52 + 1,608；反向验证每个指针指向的串 |

## 12. 一句话总结

> 改文本只有两种意外：
> **放不下**，和**搬走之后还有人指着旧地址**。
>
> 放不下 → 找空洞或搬走；
> 有人指着 → 把引用点找全，**在数据里就改数据，在指令里就改指令**。
>
> 这两件事做完，剩下的都只是翻译本身。
>
> 这套逻辑跟文件叫什么、跑在什么 CPU 上无关 ——
> `EBOOT.BIN`、`.prx`、`.sprx`（PSP / MIPS），`eboot.bin`、`.self`（PSVita / ARMv7-A），
> 全都逃不出这两条。差别只是换算基准（PSP 的 `+0xA0` / `+0xC0`，
> PSVita 要先脱壳、再按 `p_offset` 算且 vaddr 从 `0x81000000` 起）、
> 指针表藏在哪里，以及"指令里那个地址"是 `lui`+`ori` 还是 `movw`+`movt`。
