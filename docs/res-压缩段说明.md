# GOD EATER PRES 工具链 —— 压缩段格式说明（gzip / dflt / blz2 / blz4）

> **配套文档**：[[res-容器格式说明]]（容器结构、组与 TOC、DLC、美版分区）。
> 本文只讲**四种压缩段的字节布局、分块算法与解压流程**，所有条目数 / 字节数均为对官方样本的**实测**结果
> （实测结论见 [8. 附录](#8-附录实测结论汇总)）。
>
> 压缩段**没有**记录在 `res` 头部 —— 判定一律靠**魔数嗅探**。

---

## 0. 一分钟速览

| 格式 | 使用版本（平台） | 魔数 | 段头 | 压缩算法（zlib 参数） | 分块 | 实测压缩对象 |
|---|---|---|---|---|---|---|
| **gzip** | Ver 0 · GEB（PSP） | `1F 8B 08` | 10 B | gzip 包装 / L9 / **memLevel 9** / wbits **31** | 单流 | **res 包** |
| **dflt** | Ver 1 · GE2 引继数据检查器（PSP） | `dflt` | 4 B | raw deflate / L9 / memLevel 8 / wbits **−15** | 单流 | **res 包** |
| **blz2** | Ver 2 / Ver 3 · GE2 系（PSP / PSV） | `blz2` | 4 B | raw deflate / L9 / memLevel 8 / wbits **−15** | **64 KB 分块** | **普通数据** |
| **blz4** | Ver 3 变体 · GE2RB / RES / 美版（PSV / PS4） | `blz4` | 32 B | zlib 包装 / L9 / memLevel 8 / wbits **15** | **64 KB 分块** | **普通数据** |

三种「包装」互不相通，**不能混用**：

```
raw deflate        ← 无头无尾，纯粹 deflate 流                （dflt / blz2 的每一块）
zlib 包装 (wbits=15)  = 2 字节 zlib 头(78 ..) + raw deflate + 4 字节 Adler-32  （blz4 的每一块）
gzip 包装 (wbits=31)  = 10 字节 gzip 头 + raw deflate + CRC32(4) + ISIZE(4)   （gzip 整段）
```

## 1. 通用概念

### 1.1 压缩段落在哪里

压缩段**不是** `res` 头部字段，而是 `res` / `rdp` 里的**一段连续字节**，有两个落点：

| 落点 | 段起点 | 段长来源 | 说明 |
|---|---|---|---|
| **rdp 数据条目** | `offset << RdpShift`（`offset` 低 28 位 = 块号） | TOC `+0x04` 的 `size`（= list 的 `size`） | 最常见 |
| **`res` 包内 local 区** | TOC `+0x00` 低 28 位（类型 `C` / `D`） | 同上 | Ver ≥ 3 的 local 数据在 `res` 包文件尾 |

> **blz2 / blz4 的段本身不记录总长**，所以「从哪里读多少字节」**必须由容器给出**
> （rdp 条目靠 TOC `size`，res 内靠 TOC 的 offset）。只有段**内部**的块表可以自解析。
> gzip / blz4 有各自的尾部或头部字段，但也**不能**用来确定段边界。

判定方式：读段首 4 字节（gzip 读 3 字节）比对魔数。
**实测**：六个包的 **60,121 条 rdp 条目**中（其中 6,171 条带压缩），「魔数嗅探结果」与工具记录的
`compressed` 标志 **100% 一致，零例外** ⇒ 嗅探可放心用于判定。

### 1.2 四种格式的分工（按 Version）

| Version | 作品 | 格式 | 压缩**对象**（实测） |
|---|---|---|---|
| 0 | GE1 | —（无压缩） | — |
| 0 | GEB | gzip | **只压 `res` 包**（43/43 条 `isRes = true`） |
| 1 | 检查器 | dflt | **只压 `res` 包**（3/3 条 `isRes = true`） |
| 2 | GE2 体験版 | —（无压缩） | — |
| 3 | GE2 正式版 | blz2 | **只压普通数据文件**（272 条全部 `isRes = false`，`res` 包一律明文） |
| 3 变体 | GE2RB / RES / 美版 | blz4 | **只压普通数据文件**（PSV 2640 条 / PS4 3213 条，全部 `isRes = false`） |

> **这是 Ver 1 → Ver 2 之间一次重要的策略翻转**：
> 早期（gzip / dflt）压缩的是 **`res` 包** —— 因为 `res` 包会被整包读入并常驻内存，
> 压小它可以**避免切换主要 `res` 包时的内存溢出**；
> 代价是「临时从 `rdp` 调一个文件」时要现场解压、拖慢加载。
> Ver 2 起 `res` 结构优化（local 移到文件尾等）后内存冗余变多，**不再压 `res` 包**，
> 改为**只压体积大、访问频率低的数据文件**（`.gim` / `.gnf` / `.ixo` / `.kst` 等）。
>
> 两个时期的**压缩率相近**（实测：gzip 40.5%、dflt 28.6%、blz2 42.0%、blz4 30.1%，均为「压缩后 / 原始」）。

### 1.3 共同点：都由原生 C zlib、level 9 产出

四种格式**全部**是 **zlib level 9** 的输出，且：

- **.NET 的 `DeflateStream` / `ZLibStream` / `GZipStream` 与 C zlib 输出不一致**
  （实测 blz2 仅 94/96 块相同、gzip 段相差 3,680 B、gzip 头 OS 字节写 `0x0A`）⇒ **不能**用于字节一致场景。
- **`zlib.NET` 1.04 / 1.0.6 亦不可用**（memLevel 硬编码、无 gzip 分支 / 无 crc32）。
- zlib **版本无关**：1.3 / 1.3.1 / 1.3.2 输出逐字节一致 ⇒ 可放心替换。
- 工具链统一走 `NativeZlib.cs`（P/Invoke `zlib1.dll`，导出符号 `deflateInit2_`，`sizeof(z_stream)=88`），
  三种入口：`GzipDeflate`(wbits=31, M9) / `RawDeflate9`(wbits=−15, M8) / `ZlibDeflate9`(wbits=15, M8)。

## 2. gzip —— Version 0 · GEB

### 2.1 段结构

```
+0x00  10 B   gzip 头，实测恒为：1F 8B 08 00 00 00 00 00 02 03
+0x0A   ..    raw deflate 流
末尾    8 B   CRC32(4, LE) + ISIZE(4, LE，= 原始长度 mod 2^32)
```

gzip 头字段（RFC 1952）：

| 偏移 | 字段 | 实测值 | 说明 |
|---|---|---|---|
| 0 | `ID1` / `ID2` | `1F 8B` | 魔数 |
| 2 | `CM` | `08` | 压缩方法 = deflate |
| 3 | `FLG` | `00` | 无文件名 / 无注释 / 无额外字段 |
| 4 | `MTIME` | `00 00 00 00` | 时间戳恒 0（可复现） |
| 8 | `XFL` | `02` | level 9 的标志（zlib 自动写） |
| 9 | `OS` | `03` | Unix —— **必须强制**，见下 |

### 2.2 压缩与解压

```
压缩：deflateInit2(level=9, method=DEFLATED, windowBits=15+16=31, memLevel=9, strategy=0)
      整段一次 deflate(Z_FINISH)  → 再把输出第 10 字节（OS）强制写成 0x03

解压：inflateInit2(windowBits=31) 逐段读到流尾（.NET 即 GZipStream）
```

- **`OS` 字节是唯一的坑**：zlib 各构建的默认值不同（`0x03` / `0x0A`），官方段**恒为 `0x03`**。
  工具链在 `GzipDeflate` 里压缩后回写 `g[9] = 0x03`。
- `MTIME` / `XFL` 由 zlib 在 level 9 下自然产出，无需手工设置。
- 段长由 rdp TOC `size` 给出；`ISIZE` 与 `CRC32` 可作解压后自校验。

### 2.3 实测（GEB，`package.rdp`）

| 项 | 值 |
|---|---|
| rdp 条目总数 | 2426 |
| **gzip 条目** | **43**（全部 `isRes = true`，即 `res` 包） |
| 原始字节 → 压缩字节 | 69,767,760 → 28,255,333（**40.5%**） |
| 最大条目 | `god_g999_Base.res` 5,169,536 → 1,843,442 |
| 头字节（全部样本） | 恒 `1f 8b 08 00 00 00 00 00 02 03` |

`res` 侧：`system.res` 的 93 条 TOC 中带 gzip 的只有 `god_menu.res` 一条（其余 gzip 条目挂在
`god_menu` 下的嵌套 `res`，如 `god_m001_Title.res` / `god_g999_Base.res`）。

## 3. dflt —— Version 1 · GE2 引继数据检查器

### 3.1 段结构

```
+0x00  4 B   ASCII "dflt"（64 66 6C 74）
+0x04  ..    raw deflate 流（整段一次压，无 zlib / gzip 包装，无长度、无校验字段）
```

**没有**尾部 CRC / ISIZE，**没有**总长字段：解压长度只能从容器拿（`res` 的 TOC `+0x1C` 或 list 的 `rawSize`）。

### 3.2 压缩与解压

```
压缩：deflateInit2(level=9, windowBits=-15, memLevel=8) → 前缀 "dflt"
解压：跳过 4 字节魔数 → inflateInit2(windowBits=-15) 读到流尾
```

与 gzip 相比只有三处不同：**魔数 4 字节而非 10 字节 gzip 头**、**raw deflate 而非 gzip 包装**、
**memLevel 8 而非 9**。压缩策略相同（整段一次压）。

### 3.3 实测（Checker，`package.rdp`）

| 项 | 值 |
|---|---|
| rdp 条目总数 | 19 |
| **dflt 条目** | **3**（全部 `isRes = true`） |
| 原始字节 → 压缩字节 | 5,778,576 → 1,653,615（**28.6%**） |
| 样本 | `god_menu.res` 242,912 → 段长 134,193 B（含 4 B 魔数，deflate 流 134,189 B） |
|  | `god_m000_Boot.res` 290,816 → 46,558 |
|  | `god_m001_Title.res` 5,244,848 → 1,472,864 |

> 该包以 **`dflt` 取代 `gzip`**（同版本号下 gzip 条目为 0），是「Version 1 = Version 0 结构 + 换压缩格式」的直接证据。

## 4. blz2 —— Version 2 / Version 3 · GE2 系

### 4.1 段结构

```
+0x00  4 B   魔数 "blz2"（62 6C 7A 32，u32 LE = 0x327A6C62）
之后重复 N 次，直到段尾：
      +0x00  2 B   u16 LE  压缩块长度 n（**压缩后**长度）
      +0x02  n B   raw deflate 块数据
```

- **无总长、无校验、无每块解压长度**：逐块 inflate 到流尾即自然结束。
- 解压后总长只记录在**外部**：`res` 的 TOC `+0x1C`（`decSize`）或 list 的 `rawSize`。

### 4.2 分块规则

```
首块长  first = len % 0x10000        （余数为 0 时首块 = 0x10000）
块数    N     = (len - first) / 0x10000 + 1
逻辑块  block[0] = data[0 .. first)
        block[i] = data[first + (i-1)*0x10000 .. +0x10000)   (i = 1 .. N-1)
若 len <= 0x10000  ⇒ 只有 1 块（此时块 = 整份数据）
```

**「首块是余数」是本格式最关键的一点**：切分不是「从头每 64 KB 一块、尾部余数」，
而是**先把余数放在最前面**，后面全是完整 64 KB 块。

### 4.3 写盘顺序（轮转）

```
写盘：  write(block[N-1])            ← 末块先写
        write(block[0])              ← 紧接着是首块（余数）
        write(block[1]) … write(block[N-2])

解压：  按文件块序取 chunk[1], chunk[2], …, chunk[N-1]，最后取 chunk[0]，依次 inflate 后拼接
        （等价于「把读到的第 0 块挪到末尾」）
```

3 块示例（`len = 180,480`，first = 49,408）：

```
逻辑块      B0=49,408  B1=65,536  B2=65,536
文件内顺序  [B2] [B0] [B1]        ← 末块、首块、中间
解压取序    chunk1=B0 → chunk2=B1 → chunk0=B2   → 49,408+65,536+65,536 = 180,480 ✓
```

> 轮转的动机与 GECV_EX 的 `BLZ2Utils` 行为一致（其轮转分支写法即「1..n-1 再接 0」）。

### 4.4 实测

| 包 | 压缩条目 | 说明 |
|---|---|---|
| GE2 `package.rdp` | **2**（`flow.conf` / `script.conf`，均 `isRes = false`） | 原始 5,792 → 2,054 B |
| GE2 `data.rdp` | **270**（`.gim` / `.kst` / `.gmo` 等，均 `isRes = false`） | 7,818,457 → 3,286,633 B（**42.0%**） |
| GE2 `system.res` 内 local 区 | **16**（`tcretab-2-2nd.pgf` / `Ssa_System_Cursor.ssq` 等） | 段落在 `res` 包内（类型 `C` / `D`） |

多块样本验证（全部通过）：

| 样本 | 原始 | 块数 | 首块实测 | 余数计算 | 一致 |
|---|---|---|---|---|---|

## 5. blz4 —— Version 3 变体 · GE2RB / RESURRECTION / 美版

### 5.1 段结构

```
+0x00   4 B   魔数 "blz4"（62 6C 7A 34，u32 LE = 0x347A6C62）
+0x04   4 B   decompSize，i32 LE = 解压后总长
+0x08   8 B   保留，实测恒 00 ×8
+0x10  16 B   原始数据的 MD5
+0x20    ..   之后重复 N 次，直到段尾：
              +0x00  2 B   u16 LE  压缩块长度 n（**压缩后**长度）
              +0x02  n B   **zlib 包装**的压缩块
```

与 blz2 的差别只有三处：**段头 32 字节**（多出 decompSize / 保留 / MD5）、
**块用 zlib 包装而非 raw deflate**、以及**解压后总长与校验都能从段头自证**。

### 5.2 分块与写盘 / 解压

**与 blz2 完全同构**，可以直接复用同一套规则：

```
首块长 first = len % 0x10000（0 则 0x10000）；N = (len - first)/0x10000 + 1
写盘   [block N-1] [block 0] [block 1] … [block N-2]
解压   chunk[1] … chunk[N-1] → chunk[0]，逐块 zlib inflate 后拼接
```

解压后**双重校验**：

1. 拼接总长 == 段头 `decompSize`；
2. `MD5(拼接结果)` == 段头 16 字节。

> 这与 blz2 的「长度只能靠外部 `decSize`」形成对比：**blz4 段是自校验的**。

## 7. 实现与打包要点

1. **必须用原生 C zlib 压缩**（`zlib1.dll` + `deflateInit2_`），否则字节不一致（见 §1.3）。
2. **u16 块长上限 65535**：blz2 / blz4 的块头是 `u16`，而 64 KB 的**不可压缩**数据经 deflate 后会略微膨胀
   （raw 约 +0.03% + 6 B，zlib 包装再多 6 B），理论上可超过 65535。
   工具链在写块时**显式检查并抛错**（`blz2：压缩块 N 字节超出 u16 块长上限`），
   实测全部官方样本均远低于该上限（块压缩后普遍只有原始的 30%～40%）。
3. **首块余数不能写成尾块**：这是与「常规 64 KB 分块」最容易写错的地方，
   写错会直接导致解压后字节序错乱（长度对得上、内容不对）。
4. **`-c o` / `-cdlc o` 复用模式**：判定「条目是否被编辑过」时，
   先把原始段**解压**再与被编辑后的明文比对（`SameAsGunzip` / `SameAsDflt`）；
   只有未编辑的条目才复用原始压缩字节 ⇒ 官方包零改动往返可 byte-identical。
5. **gzip 的 `OS` 字节**必须回写 `0x03`（见 §2.2）。

## 8. 附录：实测结论汇总

以下结论来自**对官方样本的全量实测**（2026-10-16，只读扫描 + 逐块解压校验，不修改任何文件）。

**① 压缩对象（`isRes` 判定）**

| 只压哪一类 | 格式 | 实测依据 |
|---|---|---|
| **只压 `res` 包** | gzip / dflt | GEB 43 / 43、Checker 3 / 3 条目全部 `isRes = true`；普通数据文件一律明文 |
| **只压普通数据文件** | blz2 / blz4 | GE2 272、PSV 2640、PS4 3213 条目全部 `isRes = false`；`res` 包一律明文 |

**② 多块样本（分块与完整性校验）**

| 样本 | 格式 | 块数 | 校验项 |
|---|---|---|---|
| GE2 `article.kst` | blz2 | 6 | 首块余数 ✓、解压总长 ✓ |
| GE2 `Event.gmo` | blz2 | 4 | 同上 |
| PSV `Event.ixo` | blz4 | 19 | 首块余数 ✓、`decompSize` ✓、MD5 ✓ |
| PS4 `Blade.gnf` | blz4 | 22 | 同上 |
| blz4 小样本 | blz4 | 3 | 同上 |

全部满足 `首块长度 == len % 0x10000`，且**写盘轮转序**与**解压拼接序**均与 §4.3 / §5.2 描述一致。

**③ 判定方式可靠性**

`compressed` 标志与段首**魔数嗅探**结果，在全部 **60121 条** rdp 条目上 **100% 一致，零例外**
⇒ 嗅探可放心用于判定。

**④ 条目与字节统计**
